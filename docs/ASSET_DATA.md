# Asset data for the game

Machine-readable data generated from the asset archives by the scripts in `tools/`. Everything
points into the original zips by path and pixel rectangle; no artwork is copied or modified.
Regenerate with the commands below. `python3 -m unittest discover -s tests` checks the data still
matches the art.

## Miniworld character animations: `data/miniworld_animations.json`

Generated by `python3 tools/miniworld_anims.py` (add `--previews` for GIFs and frame strips in
`out/miniworld_anims/`). It covers all 44 soldier and worker sheets in `MiniWorldSprites.zip`.

```jsonc
{
  "directions": ["down", "up", "right", "left"],
  "sheets": [ { "file": "MiniWorldSprites/Characters/.../SwordsmanRed.png",
                "layout": "swordsman", "team": "red" }, ... ],
  "layouts": {
    "swordsman": {
      "cell": 16, "sheet_size": [80, 192],
      "animations": {
        "walk": {
          "loop": true, "frame_ms": 200, "timing": "guide",
          "directional": true, "uncertain": null,
          "frames": { "down": [ { "x": 16, "y": 0, "w": 16, "h": 16, "origin": [0, 0] }, ... ],
                      "up": [...], "right": [...], "left": [...] },
          "edge_contact": [ ... ]          // optional, see below
        } } } }
}
```

### Using it in an engine

1. Load the JSON once. For a unit, look up its sheet entry, then `layouts[sheet.layout]`.
2. Pick an animation and a direction. Non-directional animations (`"directional": false`) use the
   single key `"any"`.
3. Advance one frame every `frame_ms` milliseconds. If `loop` is false, hold the last frame (or
   switch back to idle) when it ends.
4. Draw frame `f` from the sheet image at
   `(unit_x - f.origin[0], unit_y - f.origin[1])`, where `(unit_x, unit_y)` is the top-left of the
   unit's cell-sized footprint (16px; 32px for the mounted knights). Most frames are one cell with
   origin `[0, 0]`. The spearman's thrusts are two cells, and the origin keeps the body still while
   the spear reaches out.

### Layouts

| Layout | Sheets | Cell | Animations |
|---|---|---|---|
| swordsman | Swordsman ×5 | 16 | idle, walk, attack, shield_idle, shield_hurt (Shade's guide) |
| assassin | Assasin ×5 | 16 | idle, walk, attack, attack_2 |
| spearman | Spearman ×5 | 16 | idle, walk, attack (2-cell thrusts), shield_idle, shield_hurt |
| axeman | Axeman ×5 | 16 | idle, walk, spin_attack, spin_attack_plain (non-directional) |
| bowman | Bowman ×5 | 16 | idle, walk, attack |
| musketeer | Musketeer ×4 | 16 | idle, walk, attack |
| mage | Mage ×5 | 16 | idle, walk, cast |
| knight | Knight ×4 | 32 | walk, idle, attack |
| ballista | Ballista ×1 | 16 | fire, move |
| farmer | Farmer ×5 | 16 | idle, walk, carry_idle, carry_walk, work |

Count = template + team colours (red, cyan, lime, purple; there is no musketeer template).

### What to trust

- `timing: "guide"` values come from Shade's `Miniworld-Guide.docx` (idle 300 ms, walk 200, attack
  100, shield idle 300, shield hit 100). `"assumed"` reuses those values for similar animations.
- `uncertain` holds a sentence wherever the art did not settle something:
  - the knight's walk/idle rows
  - the mage's idle/walk split (only 4 columns)
  - the axeman spin, read as a 360-degree attack
  - the assassin's second attack
  - the farmer's carry rows, and its "up" work row, which looks front-facing
  - the ballista's down/up rows
- Side rows are not always in the same order. Idle and walk rows run down, up, right, left, but the
  bowman and mage attack rows run down, up, **left, right**, and knight blocks run down, right, left,
  up. The JSON already accounts for this. These orders were checked against arrow, slash and muzzle
  directions and the frame-strip previews.
- `edge_contact` lists frames whose artwork touches pixels outside the frame:
  - **Slash and swoosh effects:** these spill 1–8 px into the neighbouring cell (swordsman,
    assassin, axeman, farmer work). Drawing the 16 px frame loses those few effect pixels; the body
    is never cut.
  - **Ballista:** its sprites fill their cells edge to edge, so its contacts are neighbours touching,
    not clipping.
- No frames are invented. Monsters and champions in the same zip are not mapped yet.

## Miniworld buildings: `data/miniworld_buildings.json`

Generated by `python3 tools/miniworld_buildings.py` (about 30 s). Add `--previews` for
`out/miniworld_buildings/buildings_contact_sheet.png`, which shows every named sprite in every
colour, and `unidentified_sprites.png`.

```jsonc
{
  "buildings": [
    { "name": "Barracks", "category": "Infantry", "uncertain": null,
      "variants": [
        { "file": "MiniWorldSprites/Buildings/Wood/Barracks.png", "rect": [16, 0, 16, 16],
          "match": 1.0, "matched_in": "...",
          "teams": { "red": { "file": ".../Red/RedBarracks.png", "rect": [16, 0, 16, 16],
                              "silhouette_iou": 1.0 }, "cyan": ..., "lime": ..., "purple": ... } },
        ... ] },
    ... ],
  "unidentified": [ { "sheet_hint": "Well", "rect": [0, 0, 16, 16], "files": [ ... 4 colours ] }, ... ],
  "not_sprite_sheets": [ ".../Enemy/Orc/AllBuildings-Preview.png" ]
}
```

### How it was built

- **Names and categories** come from the 28 rows of the building table in Shade's
  `Miniworld-Guide.docx`, kept in the guide's order. Each row has a small picture, usually two or
  three variants side by side.
- **Locating the art:** each picture was located in the sheets by exact pixel matching. Some pictures
  are assembled from tiles in different places, so they were matched tile by tile; Fruit Shop and
  Tavern are examples.
- **Splitting into sprites:**
  - Side-by-side tiles are one sprite unless every touching pixel pair at their edge is dark outline
    on both sides. Archery, Shipyard, Castle and Mausoleum are multi-tile buildings.
  - Stacked tiles are one sprite only where interior colours meet across the edge.
- **Team colours:** the same building in the red, cyan, lime and purple sheets is at the same
  position, confirmed by silhouette overlap of at least 0.85. Wood is the primary version; the
  Mausoleum exists only in `Enemy/`.

### Results and limits

- **28 of 28 guide buildings found, 60 sprites.** 27 buildings match the guide pixel for pixel.
- **Mining Shaft / Quarry is marked `uncertain`.** Its guide picture only matches its closest sprites
  at 83%, so the guide probably shows an older drawing.
- **73 sprite positions are `unidentified`:** wells, ships, docks, keeps, towers, wall pieces, the
  orc spear wall, CaveV2 and extra house/tavern variants. They are listed with the sheet name as a
  hint rather than a guessed building name. Their rectangles are best-effort groupings: a few rows of
  touching pieces (CaveV2, wall segments, docks) stay grouped.
- `Enemy/Orc/AllBuildings-Preview.png` is a preview image, not a sprite sheet, and is not split.

### Using it in an engine

Look up a building by `name` and pick a variant. Draw `rect` from `file` for the neutral wood version,
or from `teams[<colour>]` for a faction. All rects are 16px-aligned, so a building occupies
`rect.w / 16` by `rect.h / 16` map cells.

## Game data formats elsewhere

The game's own data files are in `game/data/` with a `format` field each (`mml-items/1`,
`mml-recipes/1`, `mml-balance/1`, `mml-village/1` and so on). One of them is a registry rather than
balance data: `game/data/resources.json` (`mml-resources/1`) defines the harvestable resource nodes
and the code-defined resource uses and sources. `tools/check_resources.py` validates it and generates
`docs/systems/RESOURCE_NODE_MANIFEST.md` and `docs/systems/RESOURCE_USAGE_REGISTRY.md` from it; the
game reads it through `ResourceNodes` (`game/scripts/core/resource_nodes.gd`).

`game/data/overworld_tiles.json` (`mml-overworld-tiles/1`) is generated by
`tools/build_overworld_tiles.py` (never hand-edited): the tile ids the run-time overworld generator
draws with, as village.json tile values (atlas * 100000 + tile id). `grass` and `cliff` (16 entries,
indexed by which of the top-left, top-right, bottom-right, bottom-left corners are cliff) come from the
free tileset's "overworld" corner wangset; `dirt_path` (16 entries, indexed by which of north, east,
south, west the road joins) from its "pathways" edge wangset; `trees` are the village's own
(trunk, top, bottom) stamps with a look group; `rock`, `flowers`, `bushes` and `sapling` are paid-tileset
tiles. `tests/test_tools.py` checks the file is what the tool writes.
