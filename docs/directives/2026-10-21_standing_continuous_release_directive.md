# Owner standing directive, 2026-10-21: continuous development, test, release and advance

Received in the session on 2026-10-21, verbatim:

> Hot Attic Games — Standing Development Directive
>
> This directive applies to My Medieval Life and all active Hot Attic Games projects.
>
> We operate on a continuous development, test, release, and advance model.
>
> 1. Do not wait for owner playtesting. My playtesting is informal and exploratory. I evaluate feel, visuals, gameplay, bugs, and whether the experience matches my vision. It is not a release gate. I may never play a particular build before the next one is finished.
>
> 2. Make reasonable decisions independently. Stop asking me to decide minor implementation details. If a farm recipe could reasonably use three logs or three logs plus stone, choose what makes the most sense for gameplay, realism, balance, and existing systems. Document the choice and continue. I will provide feedback if I dislike it.
>
> 3. Escalate only consequential decisions. Ask me when a choice fundamentally changes the game's vision, contradicts an explicit owner decision, introduces significant cost, or creates an irreversible architectural commitment. Otherwise, use sound judgment. If one decision is blocked, continue other approved work.
>
> 4. Finish and release complete milestones. Complete the assigned scope, run appropriate automated tests and simulations, reuse valid existing test evidence, fix genuine blockers, and publish the finished APK, Windows, and Linux packages to the actual GitHub Releases tab. Do not substitute development builds for scheduled full releases.
>
> 5. Keep development moving. Once Build 16 is completed and released, proceed with approved Build 17 development without waiting for me to test Build 16. Apply the same principle to Builds 18, 19, and beyond. Work on independent approved tasks while other tasks are blocked.
>
> 6. Avoid unnecessary testing and administrative overhead. Do not repeatedly run passing test suites against unchanged code. Do not interrupt active workers for status reports that can be obtained from GitHub. Preserve work through commits and pushes to the appropriate remote branches.
>
> 7. Treat owner feedback as continuous improvement. If I discover an issue while playing an older build, check whether it exists in the latest version and incorporate the necessary correction into active development.
>
> Immediate priority: Complete all Build 16 requirements, validate the finished implementation, and publish the full three-platform Build 16 release as quickly as practical, targeting completion by 5:30 PM Eastern on October 21, 2026. Earlier is preferred. Do not sacrifice correctness to meet the target.
>
> The operating principle is simple: Make decisions, keep developing, finish milestones, publish releases, and move forward. Do not make me the bottleneck.
